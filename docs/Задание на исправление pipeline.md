# Техническое задание: пайплайн поиска, обогащения, дедубликации и скоринга вакансий

## Цель

Собрать автоматизированный пайплайн для поиска релевантных вакансий, первичной фильтрации, извлечения полного текста вакансии, нормализации данных, дедубликации и расчёта Score относительно резюме кандидата.

На этом этапе НЕ требуется писать сопроводительные письма.

---

## Общая логика пайплайна

Пайплайн состоит из 6 этапов:

1. Быстрый поиск вакансий через crawler.
2. Ручной запуск обогащения текстом вакансии.
3. Нормализация вакансии через LLM.
4. Дедубликация относительно эталонной таблицы.
5. Скоринг вакансии относительно резюме.
6. Перенос подходящих вакансий в эталонную таблицу.

---

# 1. Автоматический поиск вакансий

## Запуск

Поиск должен запускаться автоматически каждый день через `cron` в 11:30 утра.

## Задача этапа

Crawler быстро проходит по списку найденных вакансий, например 198 позиций, и записывает в черновую таблицу только базовые сырые данные.

## Что записывать в черновую таблицу

Минимальный набор полей:

- `source`
- `platform`
- `company_name`
- `job_title`
- `job_url`
- `location_raw`
- `role_match`
- `created_at`
- `pipeline_status`

## Требование

На этом этапе не нужно открывать каждую вакансию и вытаскивать полный текст. Этап должен быть быстрым.

---

# 2. Обогащение вакансии полным текстом

## Запуск

Этот этап запускается вручную.

Перед запуском агент должен проверить:

- сколько новых вакансий есть в черновой таблице;
- у скольких вакансий отсутствует полный текст;
- какие вакансии уже обработаны;
- нет ли ошибок в ссылках;
- какие источники требуют обхода через Playwright.

## Задача этапа

Для каждой вакансии из черновой таблицы, где отсутствует полный текст, нужно получить:

- основной текст вакансии;
- весь текст страницы;
- текст из шапки вакансии;
- данные о формате работы;
- данные о локации;
- данные о зарплате;
- дополнительные блоки страницы.

## Инструменты

Можно использовать:

- JobSpy;
- Playwright;
- requests / BeautifulSoup;
- кастомный crawler;
- fallback-скрипт для сложных страниц.

## Важно

Часто важные данные находятся не в основном описании вакансии, а в отдельных блоках страницы: шапка, sidebar, карточка компании, теги, location block, salary block.

Поэтому нужно сохранять не только `job_description`, но и `page_text_full`.

# 3. Нормализация вакансии через LLM

## Запуск

Этап запускается вручную после проверки наличия полного текста.

## Задача

LLM должна разложить вакансию на структурированные поля таблицы.

## Входные данные

- `job_title`
- `company_name`
- `job_url`
- `job_description`
- `page_text_full`
- `location_raw`
- `platform`

## Выходные поля

- `normalized_title`
- `seniority`
- `function`
- `domain`
- `industry`
- `employment_type`
- `work_format`
- `location_normalized`
- `country`
- `remote_allowed`
- `hybrid_allowed`
- `relocation_required`
- `salary_min`
- `salary_max`
- `salary_currency`
- `english_required`
- `product_type`
- `b2b_or_b2c`
- `ai_related`
- `fintech_related`
- `growth_related`
- `monetization_related`
- `platform_related`
- `technical_depth`
- `management_scope`
- `must_have_requirements`
- `nice_to_have_requirements`
- `responsibilities`
- `red_flags`
- `positive_signals`
- `normalization_confidence`

## Требование

Если данных нет, не придумывать. Заполнять `null` или `unknown`.

# 4. Дедубликация

## Запуск

Этап запускается вручную после нормализации.

## Цель

Проверить, есть ли вакансия уже в эталонной таблице.

## Логика дедубликации

Дедубликация проводится в два шага.

### Шаг 1: проверка по компании

Так как обычно у одной компании есть только одна релевантная вакансия, сначала нужно найти все вакансии из эталонной таблицы с таким же или похожим `company_name`.

Сравнение компании должно учитывать:

- разные написания;
- регистр;
- юридические суффиксы;
- пробелы;
- сокращения;
- домен компании, если доступен.

### Шаг 2: проверка по title

Если компания найдена в эталонной таблице, нужно сравнить:

- `job_title`
- `normalized_title`
- `job_url`
- `platform`
- `location`
- `seniority`

## Результат

Если вакансия уже есть в эталонной таблице, в черновой таблице поставить:

- `pipeline_status = Dubl`
- `duplicate_of_id = id вакансии из эталонной таблицы`
- `duplicate_reason`

Если дубликат не найден:

- `pipeline_status = Ready for scoring`

# 5. Скоринг вакансии

## Запуск

Этап запускается вручную после дедубликации.

## Какие вакансии скорить

Скоринг проводится только для вакансий, где:

- `pipeline_status != Dubl`
- есть полный текст вакансии;
- есть нормализованные данные.

## Задача

Рассчитать числовой `Score` относительно резюме кандидата.

## Выходные данные

- `score`
- `score_summary`
- `score_positive_factors`
- `score_negative_factors`
- `score_risks`
- `score_confidence`

## Требование к `score_summary`

Короткий тезис: почему вакансия получила такую оценку.

Пример:

> Хорошее совпадение по B2B SaaS, AI-продуктам и product ownership. Слабые места: требуется глубокий опыт payroll и локальный рынок UK. Общая релевантность высокая, но есть доменный гэп.

## Важно

Оценка должна сравниваться с резюме кандидата, а не только с абстрактной релевантностью вакансии.

---

# 6. Перенос в эталонную таблицу

## Запуск

Этап запускается вручную после скоринга.

## Условие переноса

В эталонную таблицу переносятся только вакансии, где:

- `pipeline_status != Dubl`
- `score > 50`
- есть полный текст вакансии;
- есть нормализованные поля;
- есть `score_summary`.

## После переноса

В черновой таблице обновить:

- `pipeline_status = Added to master`
- `master_table_id`
- `added_to_master_at`

---

# 7. Что НЕ делать

На этих этапах запрещено:

- писать сопроводительные письма;
- генерировать ответы на вопросы анкеты;
- отправлять отклики;
- менять эталонную таблицу без прохождения дедубликации;
- скорить вакансии без полного текста;
- придумывать отсутствующие данные.

---

# 8. Ручные команды агента

Агент должен поддерживать отдельные команды:

## `check_status`

Проверить текущее состояние пайплайна:

- сколько вакансий в черновой таблице;
- сколько без текста;
- сколько нормализовано;
- сколько дублей;
- сколько готово к скорингу;
- сколько со score > 50;
- сколько готово к переносу.

## `enrich_texts`

Запустить извлечение полного текста вакансий.

## `normalize_jobs`

Запустить нормализацию вакансий через LLM.

## `deduplicate_jobs`

Запустить дедубликацию относительно эталонной таблицы.

## `score_jobs`

Запустить скоринг вакансий относительно резюме.

## `promote_to_master`

Перенести подходящие вакансии в эталонную таблицу.

---

# 9. Требования к логированию

Каждый этап должен писать лог:

- время запуска;
- количество обработанных вакансий;
- количество ошибок;
- список проблемных URL;
- количество успешно обновлённых строк;
- итоговый статус.

---
